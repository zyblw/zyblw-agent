
可以。先给你一个最关键的结论：

**这张图不是在说“zyblw-agent 要新增这么多模块”，而是在给整个 Agent Runtime 划职责边界。**

它解决的是一个非常长期的问题：

> 当模型、RAG、Memory、Browser、MCP、Computer Use、Multi-Agent、Workflow、Sandbox、Skills 等能力越来越多时，怎么保证框架不是越来越乱，而是新能力可以不断加入，最核心的执行可靠性却越来越稳定。

你可以把整个架构理解为：

> **上面负责“定义这个 Agent 是谁、拥有什么能力”；中间负责“可靠地决定下一步做什么”；下面负责“真的把事情做掉”；旁边的 Durable Control 负责“机器挂了、重复执行、多 Worker 抢任务时仍然不乱”。**

---

# 一、先纠正这张图一个容易误解的地方

图里 `Durable Control` 画在最下面，看起来好像：

```text
Agent
 ↓
执行
 ↓
最后才保存数据库
```

其实不是。

更加准确的结构应该是：

```text
                 AgentDefinition
                        │
                        ▼
                 AgentCompiler
                        │
                        ▼
                 CapabilityGraph
                        │
                        ▼
              CompositionManifest
                        │
                        ▼

               ┌────────────────┐
               │  AgentKernel   │
               └───────┬────────┘
                       │
                KernelDecision
                       │
                       ▼
               ┌────────────────┐
               │ RuntimeDriver  │
               └───────┬────────┘
                       │
              ┌────────┼─────────┐
              ▼        ▼         ▼
            Model     Tools     Context
              │        │         │
              └────────┼─────────┘
                       │

       ╔════════════════════════════════╗
       ║        Durable Control         ║
       ║                                ║
       ║ RunStore / CommandStore        ║
       ║ Worker / Lease / Fencing       ║
       ║ Ledger / Event / Recovery      ║
       ╚════════════════════════════════╝
            ↑                ↑
            └──包围整个运行过程──┘
```

也就是说：

**Durable Control 是整个 Runtime 的“可靠运行外壳”，而不是最后一个步骤。**

这个区别很重要。

---

# 二、先从整体上看：其实只有四个问题

整套架构实际上只是在回答四个问题：

| 问题                                              | 谁负责                                           |
| ------------------------------------------------- | ------------------------------------------------ |
| 这个 Agent 是什么、有什么能力？                   | `AgentDefinition / Compiler / CapabilityGraph` |
| 这次 Run 到底按照什么版本、配置执行？             | `CompositionManifest`                          |
| 当前状态下下一步应该干什么？                      | `AgentKernel`                                  |
| 怎么真正调用模型、工具、RAG，并且崩溃后还能继续？ | `RuntimeDriver + Durable Control`              |

所以这套架构并不复杂。

真正复杂的是 Agent 业务。

架构本身反而是在**把复杂性关进不同的笼子里**。

---

# 三、第一层：AgentDefinition —— “这个 Agent 是谁”

最上面的：

```text
AgentDefinition
```

可以理解成：

> **Agent 的声明文件。**

它不是运行过程，也不是 AgentState。

它描述的是：

```text
这个 Agent 叫什么
它负责什么
允许使用哪些能力
模型有什么要求
有哪些基础 Instructions
预算是多少
安全规则是什么
```

例如你的中医 Agent：

```scala
AgentDefinition(
  id = "tcm-assistant",
  capabilities = Set(
    "tcm-rag",
    "meridian",
    "acupoint",
    "anatomy-3d"
  ),
  modelRequirement = ...,
  budget = ...
)
```

Amazon Agent：

```scala
AgentDefinition(
  id = "amazon-operator",
  capabilities = Set(
    "orders",
    "inventory",
    "refund",
    "finance"
  )
)
```

它解决的是：

> **业务层应该描述 Agent，而不是操纵 Runtime。**

这非常重要。

业务开发者应该写：

```text
我要一个 Amazon Refund Agent
```

而不是写：

```text
先加载 ToolRegistry
再初始化 Context
再注册 Guardrail
再创建 Runtime
再创建 Worker
……
```

---

# 四、AgentCompiler —— 它不是“编译 Scala 代码”

这里的 Compiler 很容易让人误解。

它真正做的是：

> **把业务声明转换成一份 Runtime 真正可以安全执行的完整配置。**

就像：

```text
源码
 ↓
编译器
 ↓
可执行程序
```

Agent 中是：

```text
AgentDefinition
 ↓
AgentCompiler
 ↓
Executable Agent Composition
```

比如你声明：

```text
amazon-refund
```

Compiler 会发现它依赖：

```text
OrderCapability
RefundCapability
ApprovalCapability
AuditCapability
```

然后继续检查：

```text
这些 Capability 存不存在？
版本是否兼容？
Tool 有没有重名？
权限声明是否有效？
有没有循环依赖？
模型是否支持 Tool Calling？
Context 有没有冲突？
```

所以 Compiler 的价值是：

> **很多错误在 Run 开始之前就失败，而不是跑到一半才发现。**

这其实和 Scala 的哲学非常一致：

> 能在装配期发现的错误，不要拖到运行期。

---

# 五、CapabilityGraph —— “Agent 拥有什么能力，以及它们之间是什么关系”

这层最值得理解。

假设：

```text
AmazonRefundCapability
```

依赖：

```text
Orders
Approval
Audit
```

而：

```text
Approval
```

又依赖：

```text
Identity
Policy
```

于是：

```text
            AmazonRefund
             /    |    \
            /     |     \
        Orders Approval Audit
                  |
             ┌────┴────┐
             ▼         ▼
          Identity   Policy
```

这就是：

# CapabilityGraph

它不是执行流程图。

这一点要特别注意。

它跟 LangGraph 那种：

```text
Node A → Node B → Node C
```

完全不是一回事。

CapabilityGraph 描述的是：

> **能力依赖关系。**

类似 ZLayer：

```text
Service A
需要 Service B + C
```

---

# 为什么这东西非常重要？

因为未来你会不断增加：

```text
Browser
ComputerUse
Sandbox
Memory
RAG
Planning
SubAgent
ToolSearch
Skills
MCP
CodeExecution
```

如果没有 CapabilityGraph，很容易变成：

```text
AgentRuntime
  if browser...
  if memory...
  if rag...
  if planning...
  if sandbox...
```

最后 Runtime 什么都知道。

而有 CapabilityGraph 后：

```text
Kernel
```

根本不需要知道：

```text
Amazon
中医
Browser
MCP
```

这些只是不同 Capability。

当前 zyblw-agent 已经有明显雏形：`RuntimeExtensions` 已经把 Tool、Skill、ApprovalReviewer、ExecutionEnvironment 等能力做成 typed extension，而且明确禁止万能 Plugin。

未来 Capability 是在这个基础上的进一步统一。

---

# 六、CompositionManifest —— “这次 Run 的锁文件”

这个概念你可以类比：

```text
package-lock.json
Cargo.lock
Docker image digest
```

AgentDefinition 说的是：

> 我想运行什么。

CompositionManifest 记录的是：

> **这次 Run 实际运行的到底是什么。**

例如：

```text
Run = 123

Agent
amazon-refund@5

Capabilities
orders@3
refund@4
approval@2

Tools
order_query@hash-A
refund_order@hash-B

Model
qwen-xxx@configuration-X

Policy
refund-policy@7

ExecutionEnvironment
production@2
```

---

## 为什么 Agent 特别需要这个？

普通 HTTP 请求可能：

```text
300ms
```

Agent Run 可能：

```text
30 秒
30 分钟
3 小时
3 天
```

比如：

```text
开始退款
 ↓
等待经理审批
 ↓
一天后继续
```

这一天中你部署了新版本。

如果没有 Manifest：

```text
昨天的任务
+
今天的新代码
```

直接混在一起。

这对于高风险业务很危险。

---

例如昨天：

```text
refund_order
最大退款 100 美元
```

今天：

```text
refund_order
最大退款 1000 美元
```

旧 Run 恢复的时候：

```text
Manifest Compare
```

发现：

```text
ToolContractChanged
```

于是：

```text
RequiresRevalidation
```

甚至：

```text
Incompatible
```

而不是偷偷继续。

当前 zyblw-agent 的 `RuntimeCompositionFingerprint` 已经在做这个方向，包括模型、Instruction、工具集合、Extension、ExecutionEnvironment、Permission、Model Routing 等漂移检查。

所以 Manifest 是现有机制的自然升级，不是凭空增加系统。

---

# 七、现在进入真正的核心：AgentKernel

如果整个 zyblw-agent 只能有一个“心脏”，就是：

```text
AgentKernel
```

但 Kernel 的职责必须非常小。

一句话：

> **根据当前权威状态和刚刚发生的结果，决定下一步应该发生什么。**

Kernel 不负责：

```text
HTTP
数据库连接
OpenAI API
Qwen API
MCP 网络
PDF
PostgreSQL
```

它只负责判断。

---

# 八、StateMachine —— Run 到底处于什么状态

Agent 不应该只靠：

```text
while(true)
```

不断调用模型。

真正 Durable Agent 必须知道：

```text
现在在哪个状态
为什么在这里
什么事件允许进入下一个状态
```

例如：

```text
Created
  ↓
Running
  ↓
AwaitingApproval
  ↓
Running
  ↓
Completed
```

或者：

```text
Running
 ↓
FailedRecoverable
 ↓
Recovering
 ↓
Running
```

StateMachine 负责：

> **哪些状态转换是合法的。**

比如：

```text
Completed
```

就不能突然：

```text
→ Running
```

除非存在明确的 Fork/Retry 语义。

这是 Agent Runtime 可靠性的根。

---

# 九、Budget —— 不是简单“统计 Token”

Budget 实际上代表：

> **这个 Agent 可以消耗多少系统资源。**

可能包括：

```text
最大模型调用次数
最大 Tool 调用次数
最大 Token
最大金额
最大运行时间
最大 ChildRun 数量
最大并发
```

例如：

```text
Research Agent
maxCost = $5
maxModelCalls = 20
maxToolCalls = 50
```

每次 Kernel 决定下一步之前：

```text
Budget
 ↓
还能执行吗？
```

如果不能：

```text
Complete / Suspend / Fail
```

而不是任由模型无限循环。

这也是 Agent 和普通 Chat Completion 的重要区别。

---

# 十、Authorization —— “模型想做”和“系统允许做”不是一回事

这是企业 Agent 极其关键的一层。

模型说：

> 调用 `refund_order`。

不能理解成：

> 系统同意退款。

Kernel 应该判断：

```text
模型建议
   ↓
Authorization
   ↓
允许？
   ↓
需要 Approval？
   ↓
拒绝？
```

例如：

```text
User scope:
amazon:read
```

即使模型加载了：

```text
refund_order
```

也不能执行。

所以：

> LLM 是 proposer，不是 authority。

这条原则我非常建议 zyblw-agent 永久坚持。

---

# 十一、Suspension —— “停下来，但任务没有死”

这是 Durable Agent 和普通程序最大的区别之一。

例如：

```text
等待老板审批
等待用户补充资料
等待 24 小时
等待 Webhook
等待另一个 Agent
```

你当然不能：

```scala
ZIO.sleep(24.hours)
```

然后让一个 Worker Fiber 挂 24 小时。

正确方式是：

```text
Running
 ↓
Suspension
 ↓
持久化
 ↓
Worker 释放
```

过了两天：

```text
外部 Signal
 ↓
Resume
 ↓
继续运行
```

所以：

```text
Suspension
```

其实是：

> **把现实世界里的“等待”变成 Durable State。**

---

# 十二、ToolPlan —— 防止模型工具调用变成混乱的即时行为

假设模型返回：

```text
1. query_order
2. query_customer
3. refund_order
```

不能直接：

```text
foreach(execute)
```

因为：

```text
哪些可以并行？
哪些有冲突？
哪些需要审批？
第三步失败怎么恢复？
第二步执行完机器崩了怎么办？
```

所以需要：

```text
ToolPlan
```

它不是 Planning Agent。

它只是：

> **模型这一轮提出的 Tool Calls 的可靠执行计划。**

例如：

```text
Step 1
order_query       READ

Step 2
customer_query    READ

Step 3
refund_order      WRITE + Approval
```

前两个：

```text
parallel
```

第三个：

```text
等待审批之后执行
```

Kernel 保存 cursor：

```text
ToolPlan current = step 3
```

机器挂掉以后也知道从哪里继续。

---

# 十三、Ledger —— “已经发生过什么”

这个词非常重要。

假设：

```text
refund_order
```

请求发出之后网络断了。

系统不能简单记录：

```text
FAILED
```

因为 Amazon 可能已经成功退款。

Ledger 要记录：

```text
EffectIntent
 ↓
Attempt
 ↓
Receipt?
 ↓
Outcome
```

结果可能是：

```text
Succeeded
Failed
Unknown
```

其中：

```text
Unknown
```

非常重要。

Unknown 的意思：

> 我已经把请求发到现实世界，但目前无法确认现实世界是否完成了操作。

这种情况下：

```text
不能盲目 Retry
```

而应该：

```text
查询外部状态
或者人工确认
```

所以 Ledger 实际上是在保护：

> **Agent 与真实世界交互的正确性。**

---

# 十四、Recovery —— 崩了以后不是“重新跑一遍”

很多 Agent 框架所谓 recovery 实际上就是：

```text
重新把 conversation 给模型
再来一次
```

对于纯聊天可以。

对于：

```text
退款
修改广告预算
修改商品价格
发送邮件
创建货件
删除库存
```

这是危险的。

真正 Recovery 应该读取：

```text
State
ToolPlan
Ledger
Manifest
Suspension
Budget
```

然后回答：

> 上一次到底进行到哪一步？

例如：

```text
模型调用完成
ToolPlan 已生成
order_query 成功
refund 尚未执行
```

那么恢复就是：

```text
从 refund 前继续
```

而不是从用户第一句话重新开始。

这也是当前 zyblw-agent durable runtime 最值得保留的部分。

---

# 十五、KernelDecision —— Kernel 和外部世界之间的“协议”

Kernel 自己不做事情。

它只产生：

```text
KernelDecision
```

你可以理解成：

> Kernel 发给 RuntimeDriver 的命令。

例如：

```text
NeedContext
NeedModel
ExecuteTool
Suspend
SpawnChild
Complete
Fail
```

非常形象地说：

```text
Kernel = 大脑

KernelDecision = 神经指令

Driver = 手脚
```

Kernel 说：

> 去查一下订单。

它不会自己发 HTTP。

---

# 十六、RuntimeDriver —— 真正把 Decision 执行掉的人

Driver 的职责就是：

> **解释 KernelDecision，并利用 ZIO 真正完成外部操作。**

例如：

```text
KernelDecision.RequestModel
```

Driver：

```text
调用 ModelInvoker
```

Kernel：

```text
RequestTool
```

Driver：

```text
ToolExecutor.execute
```

Kernel：

```text
NeedContext
```

Driver：

```text
ContextAssembler.build
```

然后把结果再交回 Kernel：

```text
Kernel
  ↓ Decision
Driver
  ↓ Effect
Result
  ↓
Kernel
```

形成一个循环。

---

# 十七、ContextAssembler —— 不是简单 `messages ++ rag`

未来 Context 会非常复杂：

```text
System Instructions
Conversation
Memory
RAG
Skills
Tool Results
Business Rules
Workflow State
Artifacts
User Context
```

如果各个模块自己：

```text
messages.append(...)
```

最终一定会失控。

ContextAssembler 统一决定：

```text
什么进入 Prompt
优先级多少
可信度多少
是否敏感
Token 占多少
是否压缩
是否缓存
```

例如：

```text
System Policy       2000 token
Current Request      500 token
RAG Evidence        6000 token
Memory              1500 token
Tool Results        3000 token
Conversation        剩余预算
```

这就是：

> Context Governance。

未来 Agent Runtime 的核心竞争力之一很可能就在这里。

---

# 十八、ModelInvoker —— 不应该只是 OpenAI Client

ModelInvoker 应该成为一个稳定的：

```text
ModelRequest → ModelResponse
```

运行边界。

它负责：

```text
provider adapter
stream
timeout
retry
fallback
usage
reasoning token
tool calling
structured output
model capability
```

Kernel 根本不知道：

```text
OpenAI
Claude
Gemini
Qwen
DeepSeek
```

Kernel 只说：

```text
我要一个满足这些 requirement 的 Model Invocation。
```

这使 Provider 可以不断变化。

---

# 十九、ToolExecutor —— 真正执行 Tool，但不是决定 Tool 能不能执行

这一层的边界也很重要。

ToolExecutor 负责：

```text
参数 decode
schema validation
timeout
retry policy
execution environment
result serialization
```

但是：

```text
是否允许执行？
```

不是 ToolExecutor 决定。

那是：

```text
Kernel / Authorization / Policy
```

决定的。

这样：

```text
ToolExecutor
```

保持“机械”。

安全判断集中在 Kernel。

---

# 二十、CapabilityRuntime —— Capability 真正运行时的容器

CapabilityGraph 是：

```text
静态能力图
```

CapabilityRuntime 是：

```text
某一个 Run 中真正激活的 Capability。
```

比如：

```text
BrowserCapability
```

静态定义可能存在。

但用户只是问：

> 今天库存如何？

根本不需要 Browser。

所以：

```text
CapabilityGraph
包含 Browser
```

并不意味着：

```text
Browser 每次都启动
```

真正需要时：

```text
activate BrowserCapability
```

创建：

```text
browser session
sandbox
resources
```

结束 Run：

```text
Scope close
```

全部释放。

这就是 On-Demand Capability 的运行基础。

---

# 二十一、StructuredConcurrency —— 这是 ZIO 非常有优势的地方

Agent 非常容易产生：

```text
模型 Stream
Tool A
Tool B
Heartbeat
Timeout
ChildRun
Telemetry
```

如果普通 Future/Thread 到处 `fork`：

```text
父任务取消了
子任务还在跑

HTTP 请求断了
Tool Fiber 还活着

测试结束了
后台 worker 还在
```

这是很常见的问题。

ZIO 的：

```text
Fiber
Scope
forkScoped
race
timeout
interrupt
```

可以让：

```text
Run
 ├─ Model Fiber
 ├─ Tool Fiber A
 └─ Tool Fiber B
```

具有明确父子关系。

父 Run 被取消：

```text
子 Fiber 一起 interrupt
资源一起 release
```

这就是：

# Structured Concurrency

也是 zyblw-agent 选择 ZIO 后真正应该发挥出来的优势，而不是仅仅把 ZIO 当成 Future 替代品。

---

# 二十二、ZIO / ZStream / Scope 这一层是什么？

它们不是 Agent 概念。

它们是：

> **整个 Runtime 的执行底座。**

简单理解：

```text
ZIO
=
一次可失败、可取消、有依赖的 Effect
```

```text
ZStream
=
持续产生数据的 Effect
```

非常适合：

```text
LLM Streaming
Run Events
SSE
```

```text
Scope
=
资源生命周期
```

非常适合：

```text
HTTP client
MCP session
Browser
Sandbox
DB transaction/resource
Fiber
```

所以：

```text
Agent Architecture
```

建立在 ZIO 的：

```text
typed effect
structured concurrency
resource safety
dependency environment
```

上。

这才叫真正 ZIO-native。

---

# 二十三、Provider / Tool Env / Context 为什么放在 Kernel 外面？

因为这些都是：

# 易变化的东西。

今天：

```text
OpenAI
```

明天：

```text
Qwen
```

以后：

```text
新的 Provider
```

Kernel 不应该改。

Tool 也是。

今天：

```text
Amazon API
```

以后：

```text
TEMU
ERP
Browser
MCP
```

Context 同理：

```text
PostgreSQL pgvector
Qdrant
Elastic
GraphRAG
Memory service
```

# 二十四、最后看 Durable Control

保存：


> 这个 Run 现在真实状态是什么？

保存：

回答：

> 外部到底要求 Runtime 做什么？

不要混。

### Worker

从 CommandStore：

```text

```

然后真正启动 Runtime。

---

### Lease

Worker 拿到任务以后不是永久拥有。

例如：

```text

lease 30 seconds
```

需要持续：

```text
heartbeat
```

证明：

> 我还活着。

---

### Heartbeat

如果：

```text
Worker A
```

挂了：

```text
heartbeat停止
```

Lease 过期。

其他 Worker：

```text
Worker B
```

可以重新 claim。

# 二十五、Fencing 是这里最重要、也最容易被忽略的东西

假设：

```text
Worker A
```

网络卡住。

数据库以为它死了。

于是：

```text
Worker B
```

接管任务。

结果几秒后：

```text
Worker A 网络恢复
```

现在两个 Worker 都认为自己可以继续。

如果没有 Fencing：

```text
A 写一次
B 写一次
```

可能造成严重重复执行。

Fencing 的意思就是：

```text
新的 Worker 获得更高 generation/token
```

例如：

```text
Worker A token = 41
Worker B token = 42
```

数据库规定：

```text
41
```

已经失效。

所以 A 再 Commit：

```text
REJECT
```

即使它还活着。

这是非常重要的分布式正确性机制。

也是当前 zyblw-agent 很有价值的设计方向。

# 二十六、现在用一个真实例子跑完整套架构

假设用户：

> 帮我把订单 A123 退款 100 美元。

整个系统的运行顺序可以这样理解：

1. `AgentDefinition`：声明这是 `amazon-refund-agent`，可以使用 Orders / Refund / Approval 等能力。
2. `AgentCompiler`：解析这些能力，检查依赖、工具、模型要求和安全配置是否合法。
3. `CapabilityGraph`：得到 `Refund → Orders + Approval + Audit` 的能力关系。
4. `CompositionManifest`：冻结这一次 Run 使用的 Refund v3、Tool Contract、Model、Policy、Permission 等版本。
5. Worker 从 `CommandStore` 拿到 Start 命令，并获得 Lease/Fencing token。
6. `AgentKernel` 看当前 State，发现还不知道订单详情，于是返回 `KernelDecision.RequestTool(order_query)`。
7. `RuntimeDriver` 通过 ToolExecutor 真正查询 Amazon，结果返回订单金额 $100。
8. Kernel 收到结果，判断退款属于写操作且风险较高，于是生成 `Suspension.Approval`。
9. State 持久化为 Suspended，Worker 被释放；一天后经理批准，Resume Command 进入 CommandStore。
10. 新 Worker 接管 Run，先核对 `CompositionManifest`；如果退款 Tool Contract 没变化，就恢复执行。Kernel 创建 Effect Intent，RuntimeDriver 调用 `refund_order`，Ledger 记录 Attempt/Receipt/Outcome，成功后 Kernel 转为 Completed。

整个过程中，即使：

```text
机器重启
Worker 崩溃
网络超时
重新部署
经理隔天才审批
```

Run 都有明确的：

```text
状态
执行位置
版本
副作用记录
权限
恢复路径
```

这就是这套架构真正想解决的问题。

# 二十七、为什么我认为这种架构“合理”？

它并不是因为组件名字多，而是因为它遵循几个非常长期的软件架构原则：

| 原则               | 这套架构怎么做到                |
| ------------------ | ------------------------------- |
| 稳定核心、变化边缘 | Kernel 不知道 OpenAI/Amazon/RAG |
| 定义与执行分离     | Definition/Compiler vs Runtime  |
| 策略与副作用分离   | Kernel vs Driver                |
| 权威状态唯一       | RunStore/AgentState             |
| 恢复可解释         | Manifest + State + Ledger       |
| 权限不可由模型决定 | Authorization 在 Kernel         |
| 并发结构化         | ZIO Fiber/Scope                 |
| 分布式防重         | Lease + Fencing                 |
| 扩展不污染核心     | CapabilityGraph                 |
| 长任务可暂停       | Suspension                      |
| 副作用可追踪       | Ledger                          |

这些原则不会随着今天流行 LangGraph、明天流行另一个框架就失效。

# 十六、所以现在最危险的不是“设计还不够先进”

恰恰相反。

```text
   │        │

           ▼
```

**Kernel 修改应该非常困难。**

这反而代表架构成熟。

# 十七、未来判断“某能力值不值得吸收”，可以只问 4 个问题

以后你看到一个新框架、新论文、新 Agent 功能，不要马上加入。

问：

1. **它解决的是 5 年以后仍然存在的问题吗？**
2. **它属于 Kernel invariant，还是只是 Capability？**
3. **没有它，会不会影响 correctness / durability / security / composability？**
4. **能否用现有 primitive 组合出来？**

如果已经可以：

```text
Capability
+
Tool
+
ChildRun
+
Suspension
+
Workflow
```

组合出来，

那：

> **不要修改 Kernel。**

这就是未来 zyblw-agent 能不能保持卓越的关键。
