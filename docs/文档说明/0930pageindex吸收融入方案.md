# 二、为什么这次融合值得考虑

## 2.1 PageIndex 带来的不是一个新检索算法，而是一种不同的知识组织方式

你目前主要采用的是：

```text
PaddleOCR-VL
      ↓
DocumentStructure
      ↓
Structure-aware Chunking
      ↓
Embedding
      ↓
PostgreSQL
      ↓
Hybrid Retrieval
      ↓
Rerank
      ↓
Context Expansion
      ↓
EvidenceBundle
```

这条路径有一个特点：

检索过程主要以 Chunk 为搜索对象。

虽然你已经保存了标题路径、父节点、相邻节点、原始页码和 Block 信息，但整套系统仍然主要围绕文本块进行检索。

PageIndex 的核心价值在于将文档的层次结构变成能够主动参与检索的索引。

用户不只是搜索与问题相似的文本，还可以根据书籍结构查找相关的章节，理解相关章节的内容范围，然后进一步获取原文。

而且 PageIndex 最新公开的 Hybrid Tree Search 并没有完全放弃向量检索，而是将节点结构与向量相关性检索结合起来。:chatgpt-content-reference{index="0"}

这说明你完全没有必要替换现有的 Embedding、pgvector 或 Qwen Rerank。

正确的融合关系应该是：

**现有混合 RAG 解决语义匹配问题，文档树解决知识定位和上下文组织问题，LLM Tree Search 为复杂查询提供额外的推理导航能力。**

这是不同能力之间的互补，而不是简单替代。

## 2.2 中医书籍恰好具有适合结构化检索的特征

假设用户询问：

“《伤寒论》关于太阳病的论述是如何从辨证逐步展开到方剂应用的？”

传统 RAG 可能找到许多相关条文。

但它没有天然的机制确保完整保留这些条文在原书中的论述顺序，以及它们所在章节之间的关系。

结构化检索则可以先找到相关篇章，再沿着原书结构查找涉及的条文。

对于另外一种问题：

“古代医书有没有描述睡觉时出汗的内容？”

现有向量检索反而可能更加合适，因为用户的现代语言与原文表达可能存在较大的差异。

因此，你的网站需要同时处理两种检索需求：

**一种是理解用户表达的含义，另一种是理解知识在原书中如何组织。**

这是我认为值得吸收 PageIndex 思想的主要原因。

# 四、我建议现在真正纳入架构的能力

下面是这次改造的核心决策。

| 能力                       | 建议           | 工程复杂度 | 主要价值                 |
| -------------------------- | -------------- | ---------- | ------------------------ |
| Document Tree              | 现在实现       | 中         | 长期结构化知识基础       |
| Node 与 Block 映射         | 现在实现       | 中         | 精确定位原文             |
| Node 与 Chunk 映射         | 现在实现       | 中         | 连接新旧检索体系         |
| 独立结构索引版本           | 现在设计并实现 | 中高       | 避免反复重建             |
| Value-based Tree Retrieval | 优先实现       | 中         | 利用现有向量结果定位章节 |
| Node Summary               | 分阶段实现     | 中         | 改善复杂文档导航         |
| LLM Tree Search            | 可选实现       | 中高       | 增强复杂结构型检索       |
| Adaptive Retrieval         | 后续实现       | 高         | 根据问题选择策略         |
| Tree Optimization          | 先实现简单规则 | 中         | 降低检索树导航成本       |

这里最值得强调的是：

**Document Tree 和 Value-based Retrieval 的优先级，高于 LLM Tree Search。**

因为前两者可以充分复用你现有的数据和检索能力。

LLM Tree Search 则会带来额外模型成本、响应延迟和较复杂的调试工作。

# 五、正式建议采用的底层架构

我建议将整个 RAG 重新明确为三个部分。

## 5.1 第一部分：Canonical Document

这是长期保存的文档知识基础。

```text
              PaddleOCR-VL
                    │
                    ▼
             Canonical Document
                    │
          ┌─────────┴─────────┐
          │                   │
          ▼                   ▼
    Document Tree        Document Blocks
          │                   │
          └─────────┬─────────┘
                    │
              Source Mapping
```

它负责保存原文结构、原始 Block、阅读顺序、页码和其他来源信息。

这里有一个很重要的原则：

**不能为了提高检索效率而改变原书的真实结构。**

例如，《伤寒论》的条文应该保留独立身份。

即使将多个条文合并成一个检索节点，也不能丢失它们原来的位置和关系。

因此，建议另外引入 Retrieval Tree。

Canonical Tree 表示真实的书籍结构。

Retrieval Tree 表示经过优化、适合机器导航的结构。

两者可以共享大部分节点，但不必完全相同。

## 5.2 第二部分：独立索引

```text
              Canonical Document
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
    Structural Index          Semantic Index
          │                         │
    Retrieval Tree              Chunk
          │                         │
    Node Summary              Embedding
          │                         │
    Node Relations           Lexical Index
          │                         │
          └────────────┬────────────┘
                       │
                 Index Mapping
```

我建议把结构索引和向量索引的构建规格分开。

例如：

```scala
StructuralIndexSpec(
    treeBuilderVersion,
    optimizationVersion,
    summaryVersion
)
```

原有的 Embedding 和 Chunk 构建规格继续独立管理。

这样更换摘要模型、优化树结构时，不一定需要重新计算已有向量。

这里存在一个值得提前确定的设计细节。

**结构索引和向量索引可以独立构建，但查询时必须使用相互兼容的版本。**

例如：

```text
RetrievalSnapshot
    ├── KnowledgeProfile A
    └── TreeGeneration B
```

该组合必须经过兼容性验证。

不能因为两套索引都处于 Ready 状态，就认为它们能够直接组合使用。

## 5.3 第三部分：可组合检索

```text
                      Query
                        │
                        ▼
                 Retrieval Planner
                        │
          ┌─────────────┴─────────────┐
          │                           │
          ▼                           ▼
   Standard Retrieval          Structural Retrieval
          │                           │
    Dense / Lexical              Value Search
          │                           │
          │                      LLM Tree Search
          │                           │
          └─────────────┬─────────────┘
                        │
                        ▼
                Candidate Resolver
                        │
                        ▼
                Candidate Fusion
                        │
                        ▼
                    Reranker
                        │
                        ▼
                 EvidenceBundle
                        │
                        ▼
                    Generator
```

这样，PageIndex 式能力只是新增的检索分支。

而不是另一套独立 RAG。

所有最终证据继续复用你现有的 `EvidenceBundle` 和 Citation 机制。

需要特别注意：树检索选中的节点，只能算候选位置。它对应的原文还需要经过证据验证，才能用于生成回答。

# 六、额外负担有多大？这是必须认真考虑的问题

引入 PageIndex 思想并非没有代价。

而且最大的负担不一定是开发工作量。

我认为需要重点考虑以下四种成本。

### 6.1 数据和存储成本

新增结构索引，意味着需要保存 TreeNode、节点关系、节点摘要和映射信息。

如果所有原文、Chunk 和摘要都重复存储，会导致不必要的数据膨胀。

所以建议：

原始文件和 PaddleOCR 解析产物作为权威来源保存。

结构索引只保存必要的节点信息、导航摘要及来源引用。

Embedding 和文本块继续复用现有存储。

**不要为了 PageIndex 新建另一套向量数据库，也不要在每个树节点中重复保存整段原文。**

对于你已经采用的 PostgreSQL，这种方式比较容易实现。

### 6.2 索引构建成本

Node Summary 需要调用模型。

假设一本书具有大量章节，摘要生成会产生额外的模型消耗。

如果每次重新索引都全部重新生成摘要，长期成本会比较高。

因此建议采用内容摘要缓存。

只有节点对应的原文或者摘要生成配置发生变化，才需要重新计算。

另外，树构建与摘要生成应该分离。

用户上传书籍时，可以先完成确定性树构建和普通 RAG 索引。

摘要生成可以作为独立任务执行。

只要不影响基础检索，就没有必要让所有书籍都等待完整的摘要构建。

### 6.3 在线检索成本

PageIndex 官方明确指出，LLM Tree Search 需要模型进行导航推理，因此可能存在较高延迟。单纯依靠摘要选择节点，还可能遗漏原始正文中的细节。:chatgpt-content-reference{index="3"}

这是我不建议默认启用 LLM Tree Search 的主要原因。

例如：

用户只是查询某个方剂的组成。

通过现有混合检索和重排就可以解决。

没有必要增加数次模型调用来完成章节导航。

所以需要明确配置：

```scala
RetrievalStrategy.Classic

RetrievalStrategy.Structural

RetrievalStrategy.Reasoned

RetrievalStrategy.Adaptive
```

其中 `Reasoned` 才允许执行额外的模型推理导航。

同时需要限制最大节点访问数量、最大模型调用次数、Token 预算和超时时间。

这些应当是执行策略的一部分，而不是散落在不同检索器里的参数。

### 6.4 长期维护成本

这是最容易低估的成本。

你需要维护的不只是新的 Tree Search 算法，还包括：

树结构质量、索引版本兼容、节点与 Chunk 的映射、权限检查、结构检索评测，以及模型升级后的效果回归。

特别是在文档重新解析、Chunker 升级或者书籍版本发生变化时，必须保证旧节点不会错误引用新内容。

因此我建议：

**这次可以较大幅度调整底层模型，但不要同时引入多套复杂搜索算法。**

数据模型的长期稳定性比第一版支持多少种 Tree Search 策略更重要。

# 八、是否值得把全部 PageIndex 能力都实现出来？

**不值得。**

PageIndex 当前的开源实现和官方产品能力并不完全相同。例如，官方文档区分本地文本 PDF 处理与 Cloud 的扫描件 OCR、图像理解和更细粒度引用能力。:chatgpt-content-reference{index="4"}

你已经选择 PaddleOCR-VL 作为主要文档解析方案。

没有必要为了融合 PageIndex，重新开发或者维护另一套复杂 PDF 提取系统。

同样，PageIndex 官方介绍了更加复杂的搜索方案，但其公开教程并不等于提供了可直接移植的全部生产实现。:chatgpt-content-reference{index="5"}

你的目标不是复刻 PageIndex。

而是为 `zyblw-agent` 补充以前缺少的结构索引与推理导航能力。

现阶段，我建议把第一轮正式开发范围收敛为：

**Document Tree + Node Mapping + Value Search + 可配置检索策略。**

节点摘要和 LLM Tree Search 可以保留明确的接口，在下一轮实现。

MCTS、复杂树优化、独立文档树数据库和通用多智能体研究系统，都没有必要纳入本轮。

另外，PageIndex 的工具集成方案值得借鉴，但它的官方文档也提醒：给智能体提供文档上下文，并不等于限制了工具实际拥有的访问权限。:chatgpt-content-reference{index="6"}

你现有的权限前置设计必须保留。不能把文档范围控制交给提示词。

# 九、我建议采用的实际开发顺序

考虑到你目前还没有进入生产环境，我建议采用一次有明确边界的架构升级，而不是无期限地逐项添加功能。

**第一阶段：完成数据模型和索引生命周期。**

把 Canonical Tree、Retrieval Tree、Node/Block/Chunk 映射、结构索引版本和发布机制设计完成。

验收条件是能够稳定地从 PaddleOCR 产物构建整本书的结构索引，并准确定位原文。

**第二阶段：接入现有混合 RAG。**

让现有向量和词法搜索结果能够映射到树节点，实现基础 Node Value Search。

同时完成统一候选处理。

此阶段就应该运行第一轮真实书籍问答评测。

**第三阶段：增加节点摘要和有界 LLM Tree Search。**

这部分采用可选配置，不改变默认检索行为。

重点测试章节导航、跨章节信息查找以及长篇书籍综合问题。

**第四阶段：根据评测实现自适应检索。**

到这一步，再根据问题类型、文档质量和请求成本选择不同检索策略。

不建议在前几个阶段就引入一个额外的 LLM Planner。

否则，你可能无法确定问答效果的变化究竟来自结构索引，还是来自新的查询改写或规划模型。

# 十、怎样判断这次融合是否真正成功

这里必须强调：**增加 Document Tree，不等于必然提高最终答案质量。**

你当前已经具有结构化切块、Rerank 和上下文扩展。

如果相关问题原本就能够正确召回原文，那么 Tree Retrieval 的额外收益可能有限。

但对于分散在多个章节、需要理解原书组织方式的问题，结构索引可能具有明显优势。

建议使用真实书籍建立专项评测。

初步准备 100～150 道经过人工审核的问题，再逐步扩展。

至少区分：

- 简单事实查询。
- 古今语义差异查询。
- 指定章节或上下文查询。
- 跨章节及跨书综合查询。
- 没有足够证据的问题。

这些问题应该分别测试现有混合 RAG、增加结构扩展后的 RAG、Value-based Tree Retrieval，以及 LLM Tree Search。

主要比较正确证据召回、引用准确性、最终答案质量、无证据拒答能力、查询延迟和模型成本。

如果某一种查询策略没有体现明确收益，就不应该因为它已经开发完成而默认启用。

同样，如果纯粹的结构扩展已经解决了大部分问题，也不必让所有查询执行昂贵的 LLM Tree Search。

**从以 Chunk 检索为中心，发展为同时支持结构化知识导航与文本块检索的可组合架构。**

这次真正值得一次性设计扎实的是文档身份、结构索引、索引版本、节点映射及统一证据处理。

至于 PageIndex 的 LLM Tree Search 和复杂搜索策略，应当作为独立、可启停的高级能力，在真实书籍评测证实其价值之后逐步加入。

这样做能够保留你现有 RAG 的成果，同时为长书阅读、复杂文献检索和未来其他业务建立更有扩展性的基础。

**建议把这次架构升级的完成标准定义为：关闭全部新功能时，原有 RAG 正常工作；只启用结构索引时，可以改善文档导航；启用高级检索时，能够用真实评测证明收益，并且随时可以回退。**

达到这个标准，比完整移植 PageIndex 更符合你当前框架的长期目标。
