可以。结合这次重新看过的 `zyblw-agent` 当前 0.9 主线，我认为 **Runtime Kernel 确实已经到了需要做一次“结构收口”的时间点**。

但这次调整的目标不应该是“再设计一套插件系统”，而应该是：

> **把已经存在的 RuntimeExtensions、Composition、ZLayer、AgentRuntime、Workflow、Harness 重新组织成一套清晰的长期内核协议：**
>
> **Stable Kernel + Typed Capability Plane + Effectful Runtime Driver + Durable State + Optional Adapters。**
>
> 这样以后出现 Skills、SubAgent、Computer Use、Browser、Code Mode、Memory、Planning、新型模型能力、新协议甚至未来未知 Agent 概念时，绝大部分都不需要继续修改 `AgentRuntimeLive`。

这也是我认为 zyblw-agent 从现在走向 1.0 最值得做的一次架构升级。

---

# 一、先说最重要的判断：不要照搬 DeepSeek Harness 的 “Everything is a Plugin”

DeepSeek Harness 当前的 Cordis 思想很漂亮：Kernel 只负责插件加载、卸载、依赖，模型、Tools、Skills、Session、Sandbox、Storage、Loop、Scheduler 甚至 UI 都是 Plugin；不同插件通过 service 和 typed event 协作。([深度求索][1])

甚至它明确把 Agent Loop 本身也设计成可替换插件，并定义 waterfall、serial、parallel、emit 等不同的事件调度语义。([GitHub][2])

这对 DeepSeek Harness 很合适。

**但是我不建议 zyblw-agent 走到这么极端。**

因为 zyblw-agent 当前最有价值的东西恰好是：

```text
RunState
+
RunStore
+
Command
+
Lease
+
Fencing
+
Budget
+
Approval
+
Tool Ledger
+
Recovery
+
Commit semantics
```

它们组成了一套**权威执行语义**。

如果连 Agent Loop、状态推进、Commit、恢复策略都可以被插件任意替换，那么：

```text
A Plugin 认为 Tool 已执行
B Plugin 认为没有执行

A Loop 在 Step 3 checkpoint
B Loop 在 Step 4 checkpoint

一个插件 short-circuit
导致 budget 未结算

一个插件捕获错误
导致 Run 状态没有进入 Failed
```

zyblw-agent 现在最重要的可靠性优势反而会被破坏。

因此我推荐的不是：

> Everything is Plugin

而是：

> **Everything extensible is a typed capability; invariants stay in the kernel.**

这个区别很重要。

---

# 二、我建议最终形成这样的架构

可以把未来的 zyblw-agent 想成六层：

```text
┌─────────────────────────────────────────────┐
│               Business Agent                │
│ AgentDefinition / AgentSpec / Use Case       │
└─────────────────────┬───────────────────────┘
                      │
             Compiled Agent Plan
                      │

│             Capability Plane                │
│                                             │

│ Guard   Model     RAG      Sandbox           │
│ Planning SubAgent Observability ...         │
│                                             │
│       ↓ materialize typed contributions     │
└─────────────────────┬───────────────────────┘
                      │
┌─────────────────────▼───────────────────────┐

│                                             │
│ Run State Machine                           │
│ Budget / Termination                        │

│ Tool-plan state                             │
│ Approval state                              │
│ Recovery semantics                          │
│ Commit invariants                           │
└─────────────────────┬───────────────────────┘
                      │ KernelOp
┌─────────────────────▼───────────────────────┐

│                                             │

│ Fiber / Scope / Stream / concurrency        │

```

这里真正稳定的是中间三层：

**Capability Contract / Agent Kernel / Runtime Driver。**

以后新增功能，大多数停留在上下两侧。

# 三、当前 zyblw-agent 其实已经有这个雏形

这是一个很好的消息。

现在的 `Extension.scala` 已经明确写着：

> 每种扩展只做这一件事，禁止万能 Plugin。

而且 Extension 拿不到：

```text
AgentRuntimeLive
RunStore
mutable kernel internals
```

当前已经存在：

```text
ToolProvider
SkillProvider
ApprovalReviewer
ToolLifecycleObserver
ExecutionEnvironment
RuntimeExtensions
ExtensionDescriptor
```

这说明你之前做的方向其实是正确的。

另外，`RuntimeCompositionFingerprint` 已经把：

```text
instruction
tool set
model
context source
extension
execution environment
permission profile
model routing
model pricing
```

纳入 Run 恢复兼容性判断，并且在 extension/environment/policy 漂移时 fail-closed。

`AgentApplication` 也明确拒绝 Service Locator 思想：Provider、Persistence、Tool、Guardrail 等仍通过 ZLayer 显式注入，生产依赖缺失不会偷偷 fallback 到 memory。

所以：

**不应该推翻这些。**

需要做的是把这些零散能力**提升成一个统一的 Capability Architecture。**

# 四、最值得做的第一项调整：把 AgentRuntimeLive 拆成“Functional Kernel + Effectful Driver”

这是我认为优先级最高的一件事。

目前：

`AgentRuntimeLive.scala`

已经大约 **103 KB**。

它现在同时承担：

```text
Run initialization
composition checking
guardrail
context
model
model routing
tool planning
tool authorization
approval
tool execution
ledger
recovery
stream
events
commit
failure handling
```

这种代码一开始没问题。

但是未来增加：

```text
on-demand capability
subagent
planning
fallback
computer use
browser
sandbox
code mode
multimodal
dynamic tool search
memory consolidation
```

以后 Runtime 会越来越难控制。

解决方法不是“再拆几个 Service”。

而是采用一个非常经典、也非常适合 Scala/ZIO 的思想：

> **Functional Core, Effectful Shell。**

Rig 当前也越来越明确地区分 portable/provider-neutral core 和实际 agent runtime，并让可序列化的 run state 与运行 driver 分离。([Docs.rs][3])

在 zyblw-agent 中可以变成：

```scala
trait AgentKernel:
  def transition(
      state: AgentState,
      input: KernelInput
  ): Either[AgentError, KernelDecision]
```

例如：

```scala
enum KernelDecision:
  case RequestContext(...)
  case RequestModel(...)
  case PrepareToolPlan(...)
  case RequestApproval(...)
  case ExecuteTools(...)
  case Complete(...)
  case Suspend(...)
  case Fail(...)
```

RuntimeDriver：

```scala
trait RuntimeDriver:
  def execute(
      decision: KernelDecision
  ): ZIO[RuntimeEnvironment, AgentError, KernelInput]
```

于是：

```text
Kernel
负责：
“现在应该发生什么”

Driver
负责：
“真正去执行它”
```

---

# 五、不要把 AgentKernel 做成 Free Monad 或抽象过度

这里也容易走向另一个极端。

我不建议搞：

```text
AgentF[A]
Free[AgentF, A]
复杂 Interpreter hierarchy
```

最后框架作者自己都不好维护。

ZIO 本身已经是很好的 effect system。

因此 Kernel 不需要做到百分之百纯。

真正应该抽纯的是：

```text
状态判断
恢复判断
tool plan state transition
approval transition
budget calculation
termination
composition compatibility
model response interpretation
```

而：

```text
DB
LLM
HTTP
Tool
Clock
Random
Stream
Fiber
```

继续交给 ZIO。

最终目标不是追求理论纯洁。

而是让：

> **AgentRuntimeLive 不再知道所有业务细节。**

# 六、第二个核心调整：引入真正的一等 `Capability`

这里可以吸收 PydanticAI，但不要照搬 Python API。

PydanticAI 现在已经正式把 Capability 定义成其主要扩展点：

> capability 是一个 reusable、composable 的 agent behavior unit。

Capability 可以贡献：

```text
tools
lifecycle hooks
instructions
model settings
model selection
```

而 Memory、Guardrail、Cost Tracking、Approval Workflow 等都可以成为 Capability。([Pydantic][4])

这个思想非常值得 zyblw-agent 吸收。

但我建议分成两个概念：

```text
Capability
        ↓
   authoring unit

Contribution
        ↓
 kernel extension unit
```

例如：

```scala
trait Capability:
  def descriptor: CapabilityDescriptor

  def materialize(
      context: CapabilityContext
  ): ZIO[Scope, CapabilityError, CapabilityContributions]
```

而：

```scala
final case class CapabilityContributions(
    instructions: Chunk[InstructionContribution],
    contexts: Chunk[ContextContributor],
    toolsets: Chunk[ToolsetContribution],
    guards: Chunk[GuardContribution],
    modelSelectors: Chunk[ModelSelectionContribution],
    approvalReviewers: Chunk[ApprovalReviewer],
    observers: Chunk[RuntimeObserver]
)
```

这样：

### Capability 可以是一个业务语义整体

例如：

```text
AmazonRefundCapability
```

包含：

```text
退款说明
订单查询 Tool
退款 Tool
approval policy
refund-specific guard
```

但是进入 Kernel 后：

```text
InstructionContribution
ToolContribution
ApprovalContribution
GuardContribution
```

仍然是强类型的。

因此不会出现：

```text
Plugin.runAnything(runtime)
```

这种万能扩展。

# 七、这其实比当前 `ExtensionKind` 更进一步

当前：

```scala
enum ExtensionKind:
  Context
  Tools
  Skills
  Guardrail
  ApprovalReview
  RunLifecycle
  ToolLifecycle
  Artifacts
  Telemetry
  ExecutionEnvironment
```

这个设计的方向是对的。

我建议：

**保留这种 Typed Extension Point。**

但再上面增加：

```text
Capability Bundle
```

所以：

```text
Capability
     │
     ├── ToolProvider
     ├── ContextContributor
     ├── Guard
     ├── Observer
     └── InstructionContributor
```

而不是：

```text
Capability extends UniversalPlugin
```

这会比 DeepSeek Harness 更符合 zyblw-agent 的可靠性目标。

# 八、ZLayer 不要替换掉，它其实就是你的 Service Dependency Graph

这一点特别重要。

DeepSeek Harness 的 Cordis 有：

```text
ctx.tools
ctx.llm
ctx.sessions
```

插件通过 `inject` 声明依赖。([GitHub][5])

Scala/ZIO 根本没必要重新实现一套：

```scala
ServiceKey[String]
ServiceRegistry
ctx.get("tools")
```

因为 ZIO 已经有：

```scala
ZEnvironment
ZLayer
Tag[A]
R in ZIO[R, E, A]
```

也就是说：

> **ZLayer 本身就是 zyblw-agent 比 Cordis 更强类型的 Dependency Graph。**

所以最终应该是：

```text
ZLayer
负责系统服务依赖

Capability
负责 Agent 行为组合

Kernel
负责执行不变量
```

三个概念不要混在一起。

这会非常干净。

# 九、第三个非常值得做的东西：Capability 生命周期

PydanticAI 目前有一个很值得借鉴的东西：

**per-run state isolation。**

Capability 在 Agent 定义上可以是配置，而真正运行时可以得到独立的 per-run instance。([Pydantic][6])

这特别适合 ZIO。

可以定义：

```text
Deployment Scope
        ↓
Capability Definition

Agent Compile Scope
        ↓
Compiled Capability

Run Scope
        ↓
CapabilityInstance

Step
        ↓
temporary execution
```

利用：

```scala
ZIO.acquireRelease
Scope
Ref
FiberRef
```

一个 Capability 可以在 Run 内安全保存临时状态。

比如：

```text
Browser session
Sandbox session
MCP connection
Planning state
Tool search cache
Memory retrieval cache
```

当 Run 结束：

```text
Scope close
→ resources release
```

不需要 Runtime 自己管理。

# 十、但是 Capability 绝对不能直接修改 AgentState

这是我认为必须写进架构原则的一条。

Capability：

**不能拿 `RunStore`。**

也不能：

```scala
store.commit(...)
state.copy(...)
```

只能返回：

```text
Contribution
Decision
Observation
```

Kernel 决定：

```text
是否接受
如何转状态
什么时候 commit
```

否则以后任何 Capability 都可能破坏：

```text
Run version
fencing
budget
approval
ledger
recovery
```

这就是 Stable Kernel 和 Plugin 系统的真正边界。

# 十一、第四个非常值得做：Typed Lifecycle，而不是“万能 Hook”

PydanticAI 当前提供：

```text
run hooks
node hooks
model request hooks
tool hooks
output hooks
tool preparation
event stream
error hooks
```

而 DeepSeek Harness 则提供不同类型的 event dispatch。([Pydantic][6])

zyblw-agent 也应该有清晰的生命周期。

但不要出现：

```scala
beforeEverything
afterEverything
aroundEverything
```

我推荐把扩展语义限制为四种：

| 类型            | 作用                             | 能否改变执行 |
| ------------- | ------------------------------ | -----: |
| `Contributor` | 添加 Context/Tool/Instruction    |     有限 |
| `Transformer` | 修改 Kernel 提供的可修改 View          |     有限 |
| `Guard`       | Allow / Deny / RequireApproval |   可以阻断 |
| `Observer`    | Telemetry/Eval/Log             |    不可以 |

例如：

```text
BeforeContextAssembly
AfterContextAssembly

BeforeModelSelection
BeforeModelRequest
AfterModelResponse

BeforeToolAuthorization
BeforeToolExecution
AfterToolExecution

BeforeCompletion
AfterCompletion
```

但是：

### `Commit`

不能 hook。

### `Fencing`

不能 hook。

### `Budget settlement`

不能绕过。

### `Run terminal transition`

不能由普通 capability 任意替换。

这样未来扩展非常灵活，又不会破坏 Kernel。

---

# 十二、Hook 顺序必须成为正式协议

这件事很容易被忽略。

如果：

```text
PIIRedaction
PromptInjectionGuard
Memory
RAG
Skills
SystemReminder
```

同时介入 Context：

到底谁先？

不能靠：

```scala
List order
```

偶然决定。

建议引入：

```text
Phase
+
before/after dependency
+
stable id tie-break
```

例如：

```text
sanitize
    ↓
authorize
    ↓
retrieve
    ↓
augment
    ↓
compact
    ↓
finalize
```

Capability 可以声明：

```text
before = memory
after = security.redaction
```

启动时做 DAG validation。

循环依赖直接启动失败。

这就是 DeepSeek Harness service dependency graph 中真正值得借鉴的部分。

---

# 十三、第五个特别值得吸收的能力：On-Demand Capability

这是我认为未来 Agent Runtime 很重要的趋势。

PydanticAI 当前已经支持 deferred/on-demand capability：平时 Prompt 里只保留一个很小的 catalog entry，需要时再加载完整 capability。([Pydantic][4])

实际上 zyblw-agent 已经有一个很好的雏形：

当前 `SkillProvider` 就是：

```text
catalog
      ↓
只展示 metadata

load(id, version)
      ↓
按需加载 Skill 正文
```

而且明确规定 Skill 不能自己授予工具。

我建议：

**把这个模式从 Skill 推广到整个 Capability Plane。**

变成：

```text
Capability Catalog
       │
       ├── amazon.orders
       ├── amazon.ads
       ├── amazon.refund
       ├── tcm.meridian
       ├── tcm.acupoint
       ├── tcm.formula
       └── browser
```

默认模型只看到：

```text
id
description
version
risk
required scopes
estimated context cost
```

需要时：

```text
load_capability("tcm.meridian")
```

然后才 materialize：

```text
instructions
tools
context sources
skill
```

这会直接解决未来：

> 100 个、500 个甚至几千个工具和业务能力不能全部塞进 Prompt。

---

# 十四、而且 On-Demand Capability 必须是“权限单调”的

这是 zyblw-agent 可以比很多框架做得更好的地方。

Capability 加载只能：

```text
缩小权限
提供已经被宿主授权的能力
```

不能：

```text
自己增加 scope
自己升级 trusted context
自己解除 Guardrail
自己改变 approval risk
```

可以建立一个非常重要的规则：

> **Runtime extension is monotonic with respect to security.**

也就是：

```text
Capability 可以增加功能
但不能扩大当前 Run 已有权限边界。
```

例如：

```text
Run scope:
amazon:read
```

模型加载：

```text
AmazonRefundCapability
```

其中：

```text
refund.issue
```

需要：

```text
amazon:refund
```

那么它可以被加载。

但 Tool 必须继续不可执行。

Capability 不可以因为自己存在就授予：

```text
amazon:refund
```

这非常适合企业系统。

---

# 十五、CompositionFingerprint 应升级为 CompositionManifest

你现在的 Fingerprint 已经做得很好。

但随着 Capability 增多，一个 SHA256 最终排障能力有限。

未来建议变成：

```text
RuntimeCompositionManifest
```

例如：

```text
Kernel version
Agent definition fingerprint

Instructions
  ├─ host@4
  └─ tcm-core@2

Capabilities
  ├─ tcm-meridian@5
  ├─ citation@3
  └─ memory@2

Tools
  ├─ search_book@contract-hash
  └─ highlight_meridian@contract-hash

Context Sources
Model Policy
Model Pricing
Execution Environment
Guard Policy
Permission Profile
```

然后：

```text
manifestFingerprint
```

只是 Manifest 的最终 digest。

这样 Recover 时，不只是：

> composition changed。

而是能输出：

```text
CapabilityChanged:
tcm-meridian@4 → tcm-meridian@5

ToolContractChanged:
highlight_meridian

ModelPolicyChanged:
standard@7 → standard@8
```

这对长期生产排障非常有价值。

---

# 十六、这里还可以进一步吸收 PydanticAI 的 Capability 合并思想

PydanticAI 现在支持同 ID Capability 的组合/覆盖语义，例如同一 Capability 可以按字段 merge，而 run-level capability 可以覆盖 agent-level capability。([Pydantic][6])

zyblw-agent 可以采用类似思想，但必须更保守。

建议三个层级：

```text
Deployment
     ↓
Agent
     ↓
Run
```

优先级：

```text
Run > Agent > Deployment
```

但：

**安全字段不能简单覆盖。**

例如：

```text
maxCost
maxToolCalls
allowedScopes
risk
```

应该采用：

```text
minimum
intersection
more restrictive wins
```

而不是：

```text
last-write-wins
```

这会形成非常漂亮的：

> **Policy Lattice / Monotonic Policy Composition**

这个概念其实非常经得起时间。

---

# 十七、Tool 层还值得继续进化成 Toolset，而不是 Tool Registry 越来越大

当前：

```text
RegisteredToolRegistry
ToolProvider
```

已经不错。

下一阶段建议增加：

```text
Toolset
```

但不要只是 List[Tool]。

Toolset 应该允许：

```text
filter
prefix
metadata decoration
approval decoration
risk decoration
dynamic visibility
lazy loading
```

PydanticAI 现在 Toolset 已经支持组合、过滤、重命名、动态工具、审批和延迟加载。([Pydantic Docs][7])

zyblw-agent 可以做到更安全：

```text
ToolStore
       ↓
Toolset
       ↓
Policy filter
       ↓
Authorization filter
       ↓
Capability filter
       ↓
Model-visible ToolView
```

注意：

```text
RegisteredTool
```

仍然是事实。

`ToolView` 只是某个 Step 模型可见的投影。

# 十八、特别值得新增：Tool Search

如果以后你的公司 Agent 有：

```text
300 个 ERP Tools
200 个 Amazon Tools
100 个 Finance Tools
几十个浏览器/MCP tools
```

不可能全部传给模型。

PydanticAI 当前已经把 Tool Search 作为 Context Management Capability，让模型按需加载工具定义。([Pydantic][4])

zyblw-agent 很适合做：

```text
ToolCatalog
      ↓
semantic / lexical search
      ↓
candidate tools
      ↓
policy / authorization
      ↓
tool definitions
```

而且可以利用你的 RAG 能力。

这比“加更多 Tool integration”重要得多。

# 十九、Context Runtime 是另一个值得做深的地方

未来 Agent 的竞争很大程度不是：

> 谁能多调用几个 Tool。

而是：

> 谁能控制 Context。

PydanticAI 当前已经把：

```text
tool search
compaction
tool output limits
cache bust detection
memory
conversation search
skills
```

都纳入 Context Management。([Pydantic][4])

zyblw-agent 当前已经有 bounded context 和 compression。

下一阶段建议让所有 Context 都成为：

```scala
ContextContribution(
  source,
  trust,
  sensitivity,
  priority,
  tokenBudget,
  cacheStability,
  expiresAt,
  payload
)
```

这样：

```text
RAG
Memory
Skill
Tool result
Conversation
Agent instructions
Business context
```

最终都走同一个：

```text
ContextAssembler
```

而不是各模块自己拼 Prompt。

---

# 二十、Tool 大结果不要进入 Prompt，应该 Artifact-first

这个功能很值得做。

例如：

```text
数据库查询 5MB
网页 3MB
PDF 提取 20MB
报表 30MB
```

不能直接变：

```text
ToolMessage(content = 30MB)
```

正确模式：

```text
Tool
 ↓
Artifact
 ↓
ArtifactReference
 ↓
Context preview
 ↓
按需 search/read
```

PydanticAI 当前也已经在做 tool output truncate / spill / summarize。([Pydantic][4])

你现在已经有 Artifact 体系。

所以这个能力与 zyblw-agent 非常契合。

---

# 二十一、Memory 不要在 Kernel 里发明复杂“认知模型”

这里我反而建议克制。

不要把：

```text
working memory
episodic memory
semantic memory
procedural memory
```

全部定义成 Kernel ADT。

这些理论以后还会变化。

Kernel 只需要稳定定义：

```text
MemoryEntry
Namespace
Owner
Scope
Provenance
Confidence
TTL
Retention
Visibility
Retrieval
WritePolicy
```

至于：

```text
Episodic
Procedural
Semantic
```

让 Memory Capability 去实现。

这就是“经得起时间”的设计。

---

# 二十二、Multi-Agent 也不要做成新的“MultiAgentEngine”

这是另一个容易大杂烩的地方。

LangGraph 当前对 Subgraph 做了一件很值得借鉴的事情：

明确区分：

```text
stateless
per invocation
per thread
```

不同的 persistence semantic。([Docs by LangChain][8])

zyblw-agent 应该从这个方向吸收。

不要：

```text
SupervisorAgent
TeamAgent
SwarmAgent
GroupChatAgent
DebateAgent
```

全部进入 core。

真正的 Kernel primitive 应该只有：

```text
ChildRun
Handoff
Join
```

例如：

```text
Parent Run
    │
    ├── ChildRun A
    ├── ChildRun B
    └── ChildRun C
          ↓
         Join
```

ChildRun 必须明确：

```text
parentRunId
causationId
budget allocation
permission subset
context subset
persistence mode
```

这样：

```text
Research Agent
Reviewer Agent
Planner Agent
Coding Agent
```

只是业务模式。

Kernel 不认识这些名字。

# 二十三、Budget 应该进一步变成“层级资源预算”

你现在已经有 Run Budget。

未来可以升级：

```text
Root Run budget
       │
       ├── model
       ├── tools
       ├── child run
       └── workflow
```

例如：

```text
总预算 $10

Planner
$1

Research children
$5

Writer
$2

reserve
$2
```

Child Run：

```text
reserve
consume
release
settle
```

这会是一个非常持久的 Runtime 能力。

比“某某 Agent Pattern”重要得多。

# 二十四、Workflow 和 Agent 应继续保持分离

你目前 README 中一句话是非常正确的：

> Workflow 不替代普通函数。

这个思想必须坚持。

LangGraph 因为历史原因是 Graph-centric。

zyblw-agent 完全没必要变成：

```text
Everything is Node
Everything is Graph
```

最终应该保持：

```text
ZIO Service
   ↓
确定性逻辑

Agent
   ↓
开放式判断

ChildRun
   ↓
角色/能力委托

Workflow
   ↓
显式 durable orchestration
```

这比统一成一种模型更健康。

---

# 二十五、但 LangGraph 有两个东西值得真正吸收

第一个是：

## persistence semantics

LangGraph 的 checkpoint 不只为 recover，还支持：

```text
Human-in-loop
Memory
Fault tolerance
Time travel
Fork
```

并且在某些节点失败时会保存其他成功节点的 pending writes，避免恢复时重复执行已经成功的节点。([Docs by LangChain][9])

zyblw-agent 不需要变成 full event sourcing。

但非常值得未来增加：

```text
RunFork
Replay
DryReplay
```

例如：

```text
production incident
       ↓
snapshot N
       ↓
fork
       ↓
FakeModel/FakeTool
       ↓
replay
```

用于：

```text
debug
eval
incident reproduction
```

但绝不能默认重放真实 side effects。

---

# 二十六、第二个是 Interrupt 统一模型

LangGraph 的 interrupt 把：

```text
approval
human input
external wait
```

统一成：

```text
Suspend
Resume
```

并依赖 durable checkpoint。([Docs by LangChain][10])

zyblw-agent 当前已经有：

```text
WaitingForApproval
Workflow Wait/Signal
Suspend
Resume
```

未来最好抽象成统一：

```text
Suspension
```

例如：

```scala
enum Suspension:
  case Approval(...)
  case HumanInput(...)
  case ExternalSignal(...)
  case Timer(...)
  case Resource(...)
```

上层：

```text
Approval
HumanTask
Workflow wait
```

只是具体类型。

这会明显减少重复机制。

---

# 二十七、特别重要：统一 Agent Trajectory

DeepSeek Harness 有一个非常值得吸收的思想：

> 每一次 Run 都有完整可追踪 trajectory，resume/fork/search/replay 围绕同一事件轨迹工作。([深度求索][1])

但 zyblw-agent 不应该复制它记录“全部 reasoning”的方式。

对于生产系统应该是：

```text
Trajectory
    │
    ├── ContextManifest
    ├── ModelCall
    ├── ToolPlan
    ├── Approval
    ├── ToolResult
    ├── ChildRun
    ├── StateTransition
    ├── Usage
    └── Artifact
```

默认：

```text
MetadataOnly
```

正文只根据：

```text
CapturePolicy
```

决定是否保存。

尤其**不要把模型私有 chain-of-thought 作为长期平台契约**。

# 二十八、Trajectory 应成为 Eval 的统一输入

这是 zyblw-agent 目前值得进一步提升的地方。

当前 Eval 已经有：

```text
dataset
trend
release gate
```

但真正强大的方向是：

```text
Run
 ↓
Normalized Trajectory
 ↓
Evaluator
```

Evaluator 可以检查：

```text
最终答案
citation
tool trajectory
cost
latency
policy
approval
retrieval evidence
number of model calls
```

这样：

```text
Production Run
Test Run
Replay Run
```

都使用同一个 evaluation contract。

这会让 zyblw-agent 的 Eval 不再只是测试工具，而成为 Runtime 的质量层。

# 二十九、Model Provider 层最值得借鉴 llm4s 的，不是 Provider 数量，而是 Capability Matrix

llm4s 当前也正在从“功能多”转向生产化，明确把 Provider capability parity、API stability、安全、可观测、JVM integration 当作 v1.0 的重点。([GitHub][11])

zyblw-agent 很适合建立：

```text
ModelCapabilities
```

例如：

```text
Streaming
ToolCalling
ParallelToolCalls
StructuredOutput
Reasoning
PromptCaching
NativeWebSearch
NativeCodeExecution
Vision
Audio
LongContext
```

然后 Agent 不说：

```text
我要 GPT-X
```

而可以说：

```text
ModelRequirement(
  tools = Required,
  structuredOutput = Required,
  reasoning = Preferred,
  context >= 128k
)
```

Router 再选择模型。

你当前其实已经开始做 Model Routing。

把它继续做成 capability-based selection 会比 provider-specific if/else 更长久。

# 三十、Model Fallback 可以做，但必须 Durable

不要简单：

```scala
modelA.catchAll(_ => modelB)
```

真正可靠的 fallback：

```text
candidate set freeze
        ↓
selection persisted
        ↓
ModelCall intent
        ↓
failure classified
        ↓
fallback decision persisted
        ↓
next attempt
```

否则 recover 后可能：

```text
第一次跑 GPT
第二次恢复跑 Qwen
第三次恢复跑 Claude
```

最后根本不知道答案怎么来的。

你当前已经保存 model routing 和 pricing fingerprint，这个基础非常好。

# 三十一、真正需要重点增强的是 Side Effect Contract

这是未来企业 Agent 的核心竞争力。

当前 sideeffects 还是 Experimental。

最终值得形成：

```text
EffectIntent
EffectKey
EffectAttempt
EffectReceipt
EffectOutcome
```

其中：

```text
Succeeded
Failed
Unknown
Compensated
```

尤其必须有：

```text
Unknown
```

例如：

```text
Amazon API request sent
网络断了
```

你不能说：

```text
Failed
```

因为订单可能已经修改成功。

也不能自动 retry。

这是生产 Agent Runtime 和普通 Agent Framework 的真正分界线。

# 三十二、Outbox / Inbox / Idempotency / Compensation 很值得继续做

核心支持：

```text

```

如何实现。

这会比所谓：

```text

```

更经得起时间。

# 三十三、Sandbox / ExecutionEnvironment 也应该提升成真正的一等边界

进入 RuntimeExtensions，而且 composition fingerprint 会检查环境变化。

这个抽象长期价值非常高。

# 三十四、PydanticAI 的 Durable Backend 思想值得设计进接口，但暂时不要马上实现

PydanticAI 目前官方 durable execution 已支持 Temporal、DBOS、Prefect、Restate、AWS Lambda Durable Functions，并且提供稳定 backend builder 给第三方 runtime。([Pydantic][12])

# 四十一、如果现在真的开始改，我建议按这个顺序推进

这是我认为风险最低、价值最高的实施路径：

1. **先抽 `AgentKernel`，不改变现有行为。** 把 `AgentRuntimeLive` 中纯状态判断、ToolPlan 状态推进、Approval、Termination、Recovery decision 抽出来，建立 equivalence tests。第一阶段数据库和 HTTP 完全不动。

2. **正式定义 `Capability / Contribution / CapabilityGraph`。** 保留当前 RuntimeExtensions，先让它成为 Capability materialize 后的底层机制，不要一次删除旧接口。

3. **升级 CompositionFingerprint → CompositionManifest。** 把 Capability、Tool contract、Context source、Model policy、ExecutionEnvironment 都结构化记录，并提供 drift diff。

4. **加入 per-run Capability instance。** 使用 `Scope + ZLayer + Ref/FiberRef`，解决 Browser、Sandbox、MCP、Planning 等未来状态能力。

5. **建立 Typed Lifecycle。** 明确 Contributor / Transformer / Guard / Observer 四类语义和固定阶段，不允许万能 middleware。

6. **把 Skill lazy loading 泛化成 On-Demand Capability。** 同时引入 `CapabilityCatalog` 和 `ToolCatalog/Search`，为以后大量 Tool/MCP/业务能力准备。

7. **统一 Suspension。** Approval / HumanInput / WorkflowSignal / Timer 逐步收敛到统一 durable suspension model。

8. **引入 ChildRun / Handoff / Join primitive。** 不开发“MultiAgentEngine”，让各种 multi-agent pattern 基于这些 primitive 组合。

9. **强化 Effect Ledger。** 把 `Unknown`、Idempotency、Outbox、Inbox、Compensation 做成可靠 side-effect contract。

10. **最后再考虑 DurableBackend SPI、Replay/Fork 和外部 Workflow Engine。** 这些属于后续扩展能力，不应该阻塞 Kernel 1.0。

> **② Typed Capability + CapabilityGraph**
> **③ CompositionManifest + Durable Compatibility**

> **⑤ Side-effect Ledger + Suspension + ChildRun**


# 最后给 zyblw-agent 一个我认为最适合的长期定位

我现在越来越不建议把它称为：

> Scala Agent Framework

更准确的未来目标应该是：

> **A ZIO-native, typed, durable and governed Agent Application Runtime for Scala/JVM.**

核心关键词只有四个：

```text
Typed
Durable
Composable
Governed
```

**Typed** 来自 Scala。

**Durable** 来自你的 Run/Command/Lease/Fencing/Ledger。

**Composable** 来自这次应该建立的 Capability Architecture。

**Governed** 来自 Permission/Approval/Budget/Guardrail/Audit。

这四项是 zyblw-agent 真正应该形成护城河的地方。

而且这次重新看源码后，我认为你实际上已经完成了这条路大概 **60%～70% 的架构准备**：`RuntimeExtensions`、`CompositionFingerprint`、`ExecutionEnvironment`、ZLayer、Tool Contract、Durable Runtime 都已经存在。现在最关键的不是推翻重来，而是把它们**收敛成一个清晰、统一、真正可扩展的 Kernel/Capability 模型**。

如果这一步做对，我认为会比继续新增 10 个模块，对 zyblw-agent 的长期价值大得多。
