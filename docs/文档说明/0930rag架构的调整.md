# 四、不要把 Canonical Tree 和 Retrieval Tree 混成一个东西

这会是整个设计里非常重要的一层。

假设一本书真实结构是：

```text
伤寒论
 └── 辨太阳病脉证并治
      ├── 第1条
      ├── 第2条
      ├── 第3条
      ├── 第4条
      ├── 第5条
      ...
      └── 第70条
```

这个结构不能因为机器觉得“节点太多”就改变。

因此应该有：

```text
Canonical Tree
```

代表原书。

再派生：

```text
Retrieval Tree
```

用于机器搜索。

例如 Retrieval Tree 可以变成：

```text
太阳病
 ├── 条文 1～12
 ├── 条文 13～28
 ├── 条文 29～45
 └── 条文 46～70
```

但是：

```text
条文 1～12
```

只是一个检索节点。

它不能成为原书真实章节。

最终引用仍然回到：

```text
第3条
第7条
第10条
```

这样的 Canonical Block。

这恰好也是 PageIndex Tree Optimization 最值得吸收的思想之一：**检索树可以为了搜索成本进行 thinning、merge、expand，而不需要把检索树当成原始文档本身。**当前 PageIndex 的 Markdown 实现会根据层级构树、计算节点 Token、做 thinning 并生成节点摘要；Flash 路线则进一步支持确定性 merge 与可选 LLM expand。:chatgpt-content-reference{index="1"}

# 十九、LLM Tree Search 应该怎么真正实现

等前面的基础完成之后，再实现它。

我建议不是自由 Agent，而是：

```text
Bounded Best-first / Beam Search
```

例如：

```text
Root
 │
 ├─ A
 ├─ B
 ├─ C
 └─ D

LLM chooses:
 B
 D

 ↓

B children
D children

 ↓

repeat
```

配置例如：

```scala
final case class TreeSearchBudget(
    maxDepth: Int,
    beamWidth: Int,
    maxVisitedNodes: Int,
    maxModelCalls: Int,
    maxInputTokens: Long,
    timeout: Duration

```

初始值可以实验：

```text
beamWidth ≈ 2~3
maxDepth ≈ 4~6
visitedNodes ≈ 15~25
```

但这些只能是 benchmark 起点，不能写成永久默认。

Tree Search Prompt 输入：

```text

Current path

Child:
  id
  title
  navigation summary
  page range
```

输出只允许：

```text
node IDs
```

不能允许模型：

```text
自己构造 nodeId
自己改变 documentId
自己扩大 tenant scope
```

所有 Node ID 必须回 Store 再认证。

# 二十、Node Summary 怎么做才不会成为负担

PageIndex 当前 Markdown 实现已经有一个合理思路：内容很短时可以直接作为 summary，超过阈值才调用模型生成摘要。:chatgpt-content-reference{index="3"}

你可以进一步做得更适合生产。

我建议：

```text
SummaryMode.Off

SummaryMode.Selective

SummaryMode.Full
```

其中默认：

```text
Selective
```

只为：

```text
非叶子节点

长节点

标题信息不足的节点
```

生成摘要。

摘要 Cache Key：

```text
nodeContentHash
+
summaryModel
+
promptVersion
```

因此重新摄取同一本书但相关节点未改变：

```text
直接复用摘要
```

不要重新调用模型。

# 二十一、Tree Optimization 第一版不要依赖 LLM

PageIndex Flash 最新方向也越来越强调确定性结构恢复；其本地 Flash 可以不用 LLM 建树，确定性 merge 也能单独运行，更复杂的 expand 才需要 LLM。:chatgpt-content-reference{index="4"}

你应该采用类似原则：

```text
Canonical Tree

       ↓

Deterministic Retrieval Optimization

       ↓

Optional LLM Optimization
```

第一版 deterministic optimizer 就够了。

可以根据：

```text
nodeTokenCount
childCount
depth
pageSpan
headingQuality
```

进行：

```text
过碎 → merge

过宽 → group

过大 → retain children

无法可靠处理 → 保持 canonical
```

绝对不要：

```text
LLM 随意重新发明书籍目录
```

# 二十三、最终业务不应该面对几十个参数

框架内部当然可以有：

```text

...
```

但业务开发者不应该每天组合这些东西。

我建议提供“Retrieval Recipe”。

例如：

| Recipe              | 实际执行                                         | 适合场景          |
| ------------------- | ------------------------------------------------ | ----------------- |
| `classic`         | Dense + Lexical + Rerank                         | FAQ、文章、短知识 |
| `book-fast`       | Classic + Node Value                             | 普通书籍问答      |
| `book-grounded`   | Classic + Value Tree + Structural Expansion      | 中医网站默认      |
| `book-deep`       | Value Tree + LLM Tree + Classic + Rerank         | 复杂章节型问题    |
| `corpus-research` | Document Discovery + per-document deep retrieval | 跨书研究          |
| `low-latency`     | Classic，限制候选和 rerank                       | 实时场景          |

而业务只需要：

```scala
RagQuery(
    text = query,
    retrievalRecipe = RetrievalRecipe.BookGrounded
)
```

或者由知识空间默认配置：

```text
TCM_BOOKS → book-grounded

BLOG → classic

FORUM → classic

RESEARCH → corpus-research
```

这才是“框架能力强，但业务容易使用”。

# 三十、这次我建议你真正按照下面顺序开发

这里我给你一个比较明确的实施次序：

1. **先升级 Canonical Document Model。** 把 `Section` 正式纳入 `DocumentStructure`，确保 PaddleOCR 的章节、Block、Page、BBox、原文顺序全部不会在解析边界后丢失，同时升级 `structureSha256` 和相关测试。
2. **建立独立 Structural Index。** 引入 `StructureBuildSpec / StructureProfileId / TreeNode / NodeChunkMapping / StructureStore`，建立 PostgreSQL 表和完整生命周期，但此时完全不做 LLM Tree Search。
3. **重构 Retrieval Runtime 的候选阶段。** 从当前 `DefaultRetriever` 抽出 `RetrievalPlanner → RetrievalBranch → CandidateMaterializer → Fusion → Rerank → Evidence`，并把内部 signal 从字符串 Map 逐步升级成强类型。
4. **实现 Value-based Structural Retrieval。** 直接复用当前 Dense/FTS 搜索结果映射节点，实现第一个真正产生业务收益的结构检索能力，并进行第一次中医书籍 A/B Eval。
5. **增强 Structure-aware Expansion。** 让 Tree 参与章节覆盖、Sibling、Ancestor、Node boundary 等上下文装配，这一阶段很可能已经能显著增强书籍问答。
6. **最后增加 Node Summary + Bounded LLM Tree Search。** 只作为高级 Branch，建立严格的模型调用次数、节点、Token、时间预算，并加入 fallback。
7. **建立 Retrieval Recipes 和 Adaptive Planner。** 将底层几十个能力组合成少量稳定业务方案，例如 `classic / book-fast / book-grounded / book-deep / corpus-research`，最终让业务开发变简单。
8. **用真实中医问题决定是否默认启用。** 对现有 Hybrid、Value Tree、Structural Expansion、LLM Tree 分别做消融实验，只有真实指标证明增益的能力才进入默认配置。

# 三十一、有一些东西我明确建议不要吸收

PageIndex 首页仍然强调 “No Vector DB / No Chunking”，但它当前官方 Hybrid Tree Search 已经使用 chunk + embedding value prediction，并将其与 LLM Tree Search 结合，且该混合方案是其 Retrieval API 的默认方向。:chatgpt-content-reference{index="5"}

所以你不要追：

| 不建议                     | 原因                                 |
| -------------------------- | ------------------------------------ |
| “Vectorless” 作为目标    | 你的中医古今语义匹配非常需要 Dense   |
| 删除 Chunk                 | Chunk 是最终精确证据的优秀单位       |
| 删除 pgvector              | 没有必要                             |
| 删除 Qwen Rerank           | Tree 并不能替代精细重排              |
| Python PageIndex Sidecar   | 增加部署、RPC、版本耦合              |
| PageIndex 特有类型进入核心 | 应使用通用 Structural Retrieval 概念 |
| LLM 自动重构原书结构       | 容易污染 Canonical Structure         |
| 默认每次 Tree Search       | 延迟与成本不划算                     |
| MCTS 第一版                | 当前没有业务证据证明需要             |
| Tree Summary 直接回答用户  | 摘要不是权威证据                     |

所以最终不是：

```text
zyblw-agent
+
PageIndex
```

而应该成为：

```text
zyblw-agent

Structural Retrieval
       ↑
吸收 PageIndex 优秀思想
```

## 最后给你一个非常明确的取舍

**值得做，而且现在做比生产以后再改合适得多。**

但这次不要把目标写成：

> “实现 PageIndex”。

应该写成：

> **“为 zyblw-agent 建立一套 production-grade Structural Retrieval Architecture，并吸收 PageIndex 在 Document Tree、Tree Optimization、Node Summary、Value Search 和 Reasoning Tree Search 上经过验证的优秀思想。”**

其中我认为现在真正必须一次做扎实的是：

**Canonical Document Structure → Structural Index → Node/Chunk Mapping → Retrieval Branch Architecture → Version/Activation Model。**

这些属于“地基”。

至于：

**Node Summary、LLM Tree Search、Adaptive Planner、复杂 Tree Optimizer**

属于“上层算法”。

这些以后换模型、换算法甚至完全推翻，都不应该再修改地基。

如果你按照这个边界来推进，这次不是继续“造工具”，而是在给你已经真正跑通的书籍问答入口补齐一块缺失的检索能力，而且这些能力以后也可以用于技术文档、企业知识库、法律文档、研究报告等其他场景。
