# 验收意图与六层验证

用于新行为、状态机或关键不变量；这些是选择验证手段的层次，不是每次都运行六套工具的门禁。

## 先确定验收

按 AGENTS 判断是否需要短变更规范；小修复可以在会话中直接写清一个回归条件。EARS 用于让条件和结果可观察，例如：

```text
WHEN 来源在检索后被撤回 THE SYSTEM SHALL 在最终投影前移除该来源。
WHILE worker 的 fencing token 已过期 THE SYSTEM SHALL 拒绝旧 worker 的写入。
```

检查现有 ID、错误、命令/事件和状态，不新建重名或平行类型。所谓 Concepts Inventory 是这次复用现有契约的核对，不强制生成新文档。

## 按风险选择验证层

| 层 | 能证明的范围 |
| --- | --- |
| 0 编译器/类型 | 调用和状态建模的类型一致性；警告强度按实际 build，不擅加 -Werror |
| 1 静态/架构规则 | 格式、依赖方向、禁用 API；只报告真正运行过的检查 |
| 2 独立 oracle | 需求边界、协议 fixture、性质、旧数据；避免将实现复制进 expected |
| 3 变异抵抗 | 推演删掉权限、翻转比较、打破编号后测试是否失败；未跑 mutation 工具就不宣称跑过 |
| 4 纯核心 | 对真实纯状态转换做重放/性质验证；类型正确不等于数学证明 |
| 5 运行轨迹 | 验证实际降级、延迟、费用与结果；没有采集和回放就报告未验证 |

同一 Agent 可以实现与写测试，关键是 oracle 的独立性，而不是形式上换一个模型。高风险修改再按授权考虑独立审核。
这些层次不能授权读取生产数据，也不能把已有但未执行的评测功能说成通过。
