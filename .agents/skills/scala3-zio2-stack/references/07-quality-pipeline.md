# Quality Pipelines for AI-Driven Engineering

Inspired by Bill Venners' (creator of ScalaTest, co-author of *Programming in Scala*) *Quality Pipelines for Generative AI* and Adam Warski's *Orca*, this guide establishes the deterministic software factory pipeline for high-throughput, zero-regression AI development in `zyblw-agent`.

---

## 1. Rule #1: What Can Be Done with Deterministic Code, NEVER Give to AI
AI excels at semantic reasoning, domain modeling, and contextual synthesis. It is notoriously unreliable and token-wasteful at mechanical, bulk text transforms.

- **BANNED for AI**:
  - Reformatting files or aligning indentation/stars manually (use `scalafmt` or `sbt scalafmtCheckAll`).
  - Classpath and dependency synchronization (use `sbt --batch bloopInstall`).
  - Raw bulk search and symbol exploration across hundreds of files (use Metals MCP or IDE index).
  - Mechanical regex replacements without invariant verification.
- **MANDATORY**:
  - Keep mechanical transformations inside deterministic Scala or Python scripts under `scripts/`.
  - Always run deterministic checks (AST invariance, schema validation, compiler passes) to verify that transformations do not alter semantics.

---

## 2. The Green Gate: Save Reviewer Tokens & Human Bandwidth
The core bottleneck of generative AI is **Human & Reviewer Bandwidth**. AI can produce code 100x faster than humans can review it.

To prevent token waste and review fatigue:
1. **Never review red code**: Code generated by a Writer Agent MUST pass the local **Green Gate** (`sbt "<module>/compile"` and unit tests) before reaching human review or expensive Reviewer Agent fleets.
2. **Deterministic Fast-Fail**: If compilation fails or tests break, immediately bounce the diff back to the Writer with compiler diagnostic logs. Never invoke secondary LLMs on code that fails the Green Gate.

```
[ Writer Agent ] ──Writes Code──► [ Green Gate: sbt compile & test ]
                                            │
                                  ┌─────────┴─────────┐
                                  ▼                   ▼
                               [ Fails ]           [ Passes ]
                                  │                   │
                        (Bounce back to Writer)       ▼
                                             [ Read-Only Reviewers ]
```

---

## 3. Role Separation: Preventing Agent Thrashing
When multiple LLMs collaborate, allowing multiple models to mutate the same workspace leads to **Agent Thrashing** (Model A refactors, Model B undoes it, generating infinite loops and corrupted git history).

Enforce strict role boundaries:
- **Writer (Generating Agent)**: Produces the initial implementation for a defined Milestone and prepares the git commit.
- **Reviewer Fleet (Audit Agents)**:
  - **Strictly Read-Only**: Reviewers CANNOT edit files.
  - **Structured Findings**: Must produce structured critique reports (JSON) containing:
    `{ file: String, line: Int, severity: "BLOCKER" | "WARN" | "SUGGESTION", reason: String }`
  - Cross-Model Diversity: Combine different models/prompts (e.g., security, performance, minimalism) to eliminate blind spots.
- **Adjudicator (Single Mutator)**:
  - Only ONE entity has write authority to address the findings (typically the Writer).
  - Evaluates the review findings, applies the necessary modifications, and sends the diff back through the Green Gate.
- **Re-review**:
  - Limited to 2-3 iterations maximum to ensure convergence.

---

## 4. Manager & Asynchronous Decision Ledger (`questions.md` / `Suspension.HumanInput`)
When an autonomous pipeline encounters an architectural crossroad, missing specification, or a high-risk fork that could waste hours of tokens, **it must never hallucinate or blindly guess**.

### The Pattern:
1. **Pause on Uncertainty**: The Agent pauses execution and creates a structured entry in `questions.md` (or triggers `Suspension.HumanInput(taskType, prompt)` in the runtime).
2. **Asynchronous Human Triage**: The human engineering manager reviews the question asynchronously (via phone, console, or chat) and provides direction in `answers.md`.
3. **Resumption**: The pipeline picks up the answer and resumes its autonomous milestone progression without loss of context.

---

## 5. Milestone-Driven Git Commits
For long-running or autonomous batch tasks (refactoring, documentation enrichment, corpus migration):
- Break the overall task into distinct, atomic **Milestones**.
- **1 Milestone = 1 Passing Green Gate = 1 Clean Git Commit**.
- If a subsequent stage fails, the pipeline can safely revert to the previous milestone commit without losing hours of work.
