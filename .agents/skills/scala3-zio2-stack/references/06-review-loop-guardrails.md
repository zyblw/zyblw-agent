# 06. 五视角检查：按风险取证

这是同一位开发者在交付代码或发起合并前执行的高效自检框架，不是自动启动 5 个 Agent 的流程要求。
只读审查时可直接依据本清单诊断失败原因；在宣称代码就绪前，必须确保通过本清单核验。

## 一、 五视角标准核检矩阵

| 审查视角 | 核心核检问题与硬性门禁 | 典型违规/拦截项 |
| :--- | :--- | :--- |
| **1. 安全防线 (Security)** | 外部输入是否完成强类型解析？租户与权限是否在数据库层强制过滤？敏感凭据与原始 Prompt 是否在日志与事故包中彻底脱敏？ | 拼接 SQL；日志打印用户密码/API 密钥；外部输入被直接当作 System 指令注入。 |
| **2. 性能与并发 (Concurrency)** | 外部并行任务是否设置了显式并发上限（`.withParallelism`）？长耗时/阻塞调用是否由 `attemptBlocking` 隔离？Scoped 资源是否确保释放？ | 裸 `foreachPar`；无超时的网络等待；死锁或连接池泄漏。 |
| **3. 类型与效应 (Types & Effects)** | 是否存在悬空丢弃的 ZIO 副作用（编译告警 `-Wnonunit-statement`）？错误通道是否使用了精准的领域 ADT？是否消除了状态的布尔盲区？ | 丢弃未执行的 effect；通配 `catchAll` 吞掉系统致命异常；用多个布尔值拼凑复合状态。 |
| **4. 最小改动 (Minimalism)** | 改动是否精准收敛于本次任务目标？是否严格遵循 R2 铁腕约束，复用了现有概念与类库？公共 API 与持久化格式是否向后兼容？ | 为修改一个方法而重构整个模块；引入未经批准的大型外部依赖；制造冗余抽象。 |
| **5. 测试信号 (Test Quality)** | 测试用例是否基于独立预言机而非照抄实现逻辑？是否具备变异抵抗能力（反转条件即失败）？是否使用虚拟时钟（TestClock）消除偶发失败？ | 测试无论逻辑对错皆通过；大量包含脆弱的 `Thread.sleep`；缺乏异常与失败路径断言。 |

## 二、 审查与交付的标准汇报格式

当完成功能开发、修复或执行代码审查时，使用以下结构化模板输出结论：

```markdown
### 五视角自查结论

- [x] **安全防线**：所有 SQL 均为参数化绑定，外部文本已脱敏并限制在 User 作用域，无凭据泄露。
- [x] **性能与并发**：批量并发限制为 `.withParallelism(8)`，阻塞调用由专用线程池隔离。
- [x] **类型与效应**：消除了悬空副作用，错误通道使用 `DomainError`，状态机采用 `enum` 建模。
- [x] **最小改动**：改动仅涉及 2 个目标文件，严格向后兼容现有 JSON 序列化格式。
- [x] **测试信号**：补充了 3 个独立预言机测试，覆盖了超时、CAS 冲突与撤回场景，全绿通过。
```

## 三、 单一修改者纪律 (Single Adjudicator)

在多 Agent 协同或人机结对环境中：
- **审查者（Reviewer）只读**：审查者只负责指出客观事实、风险文件与具体行号，提出改进建议，**严禁私自修改业务代码**；
- **修改归一人**：所有代码变更统一由单一实施者（人类或主修改 Agent）执行，防止多人并发改动造成不可逆的逻辑回滚或破坏工作树。
